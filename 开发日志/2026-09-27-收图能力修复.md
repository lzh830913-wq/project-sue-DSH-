## 一句话

**不是模型不支持，也不是配置写错——是 DSH 的 `dsh-llm-deepseek` 适配器把 `inputModalities` 硬编码成 `["text"]`，配置里写的 `inputModalities: ["text","image"]` 会先被它的 schema 丢掉、再被 `modelInfo()` 覆盖**。改用 `dsh-llm-pi-ai` 的 DeepSeek 路由（它的 schema 认 `input` 字段并如实上报）才能让收图能力真实存在。

## 背景（为什么值得记）

- 症状极具误导性：报错说「模型不支持图片」，而 **DeepSeek-V4.1-Flash 本身是原生多模态**（[官方发布说明](https://api-docs.deepseek.com/zh-cn/news/news260910/)、[Vision API 用法](https://apidog.com/blog/deepseek-v4-1-flash-vision-api/)），跑的还是更专门的 `deepseek-v4-flash-vision-exp` 变体。
- 老刘改了配置、重启了进程，报错不变——**因为改的那几行根本读不进去**。
- 两条独立路径都复现同一条错误：GUI 发图（`prompt` 校验）与工具 `read_image`（fs 工具校验），说明卡点在**元数据**这一层，不在 UI 或会话历史。

## 教训（进「已知坑」）

1. **配置写对了，不代表读得进去**：schema 是白名单，未声明的字段会被静默丢弃。**判断一个配置项是否生效，要看读它的那行代码，不要看文档（或注释）**。
2. **报错信息会甩锅给模型**：`MODEL_DOES_NOT_SUPPORT_IMAGES` 实际是「**适配器元数据**没声明图片」——模型无辜。遇到这类错，先找到**产出该元数据的那行代码**。
3. **同一能力在不同适配器上不等价**：`deepseek-official` vs `pi-ai` 两条路，收图能力一条有、一条没有。跨适配器迁移功能时，**能力面要逐条核**，不能假设「同一个模型名，行为一样」。
4. **重启不解决配置不生效**：改配置无效时，区分「没重载」和「读不到」——本次是后者，重启一百次也没用。

## 补记（同日 · 定案修正）：真正的根因是**版本旧**，不是适配器永久不支持

> 老刘一句话点破了：**「3081 那边完全可以看图，最大的差异是它的 DSH 版本新一些。」**
> 查证结论：**他对。** 我上面查的 `dsh-llm-deepseek` 是**0.1.0-rc.6** 的代码——一个旧版本的缺陷，不是永久事实。

### 版本对照（本机实读 package.json）

| | `dsh` | `dsh-llm-deepseek` | 收图 |
|---|---|---|---|
| **3081（雯）** | 0.1.1-rc.2 | 0.1.1-rc.2 | ✅ 完整支持 |
| 3080 启动器实际指向 | **0.1.0-rc.6** | 0.1.0-rc.6 | ❌ 硬编码 text |
| 3080 本机另一个缓存 | 0.1.1-rc.2（`de4831d60afe10da`，2026-09-01 就下好了） | 0.1.1-rc.2 | ✅ |

**0.1.1-rc.2 的适配器确实完整支持收图**（`lib/index.js` 实读）：

```js
L1619  inputModalities: z.array(z.union(MODEL_MODALITIES)).min(1).default(["text"])   // schema 收这个字段了
L1620  imagePixelBudget: z.number().step(1).min(1)
L1621  imageMaxBytes: z.number().step(1).min(1)
L1286  inputModalities: model.inputModalities ?? ["text"]                              // 元数据如实上报
L1396  ...?.inputModalities?.includes("image") !== true → UNSUPPORTED_CONTENT           // 发图前按声明校验
L1678  inputModalities: [...inputModalities]                                            // 解析后保留
```

对照我这边 rc.6 的版本：整个文件里 `inputModalities` **只出现两次，两次都是硬编码 `["text"]`**——schema 里根本没有这个字段。**所以之前的结论要精确化：不是「适配器永远不支持」，而是「rc.6 那一版还没做，0.1.1-rc.2 起做好了」。**

### 真正的根因：启动器指着旧缓存

### 教训（比上面四条更重要，放最后）

5. **判断「缺陷」之前先确认版本**：同一个包名在不同版本上能力不同，我全程只读了**当前进程挂的那一份缓存**，就下了「适配器把能力写死」的结论——结论对了一半，定性错了（是旧版未实现，不是设计缺陷）。**下一步应该是比版本，而不是立刻找绕行方案。**
6. **绕行方案要标注有效期**：pi-ai 路由能通，但它解决的是「旧版本缺功能」，升级才是正路。**遇到能力缺失，先问「上游新版有没有」，再问「有没有别条路」。**
7. **注释会说谎**：bat 注释写着 0.1.1-rc.2，实际路径是 rc.6。**版本要从 `package.json` 或缓存目录名读，不能信注释。**

## 附带教训（同日 · 我自己踩的第二次）：脚本文件的编码坑

改完 bat 后，老刘双击启动，黑窗报了一句乱码错误：

```
'鏈猴紝鏀瑰洖' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

**根因**：我用 UTF-8 写的**中文注释**，而 cmd.exe 按 **OEM 代码页（本机 GBK）** 读 `.bat`——中文注释被解码成乱码，乱码里恰好出现被当作命令执行的内容。bat 仍能跑起来（乱码行只报错，后面的 `node` 行照常执行），但这是**纯粹的、可避免的噪音**。

**这条教训 2026-09-23 已经因 `.ps1` 记过一次**（PS 5.1 按 ANSI 读无 BOM UTF-8，中文字节吃引号），我写 `.bat` 时没想到同一条规则适用——**这是我的执行失误，不是新坑**。

**已固化**（写进 `skills/engineering/SKILL.md` 第 10 条 + `进度快照.md` 已知坑）：

- `.bat` / `.cmd` / `.ps1` **一律纯 ASCII**，注释也用英文；
- **判据**：**命令位置必须 ASCII**——字符串参数里的中文不属于批处理自身的字节，是安全的；**注释是最危险的位置**（最容易被误判为无害）；
- **验证**：写完扫字节，非 ASCII 计数必须为 0：

  ```powershell
  ([System.IO.File]::ReadAllBytes($p) | Where-Object { $_ -gt 127 }).Count   # 必须是 0
  ```

- **现状核对**（2026-09-27 全盘扫描）：本机脚本文件只有 `I:\SUE test\memory\verify-memory-recall.ps1` 含 582 个非 ASCII 字节——中文都在字符串里、9/23 已验收跑通，**暂不改**；工作区两个启动 bat 均已确认 0 非 ASCII 字节。
