# 2026-11-08 · rofm 空转诊断与记忆分工定案

> 起点：老刘问「rofm 有工作吗」，顺带带来消息——3081 装了 dsh-living-memory。问诊变体检，体检牵出两个发现、一个决定、一行修复。

## 一、rofm 空转——证据链（全部实测，非印象）

- 装机（10-28）至 11-08：**51 轮 recall 全部 `matchedFolders:0`**；两个会话的 `index.json` 均 `folders:[]` —— 零归档
- 跨会话搜索实测：搜「身体反馈 方案」→ 唯一命中=当前会话里我自己几分钟前的查询文本（**自回显假阳性**）；直接深挖上一页会话（session-90cd…）「界定锚/宪法」= **0 命中**（该话题今天上午在那一页长谈过）
- **根因**：`compress.triggerPercent=75` 的分母是**窗口**（host 提供 = 1M tokens）→ 触发点 750k tokens；上一页 11 天峰值 ~19.2 万字符（约 15% 窗口），**手动共识翻页永远先到** → compress 一次没跑 → folders 恒空 → recall 无米下锅、跨会话搜索只剩当前会话的活事件索引
- 同构教训（10-28 节点）：「归档是 rofm 唯一记忆来源，保护性关闭=功能空转」——这次不是被关，是**阈值物理上够不着**。功能空转的另一种形态；**判功能不能只看「在跑」，要看产出**。

## 二、修复（一行 + 备份 + 判据 + 生效时机）

- 改动：`C:\Users\lzh_6\.dsh\profiles\web\node_modules\dsh-rofm\config.json` 的 `compress.contextWindowTokens: 0 → 128000`（0=用 host 窗口；>0=覆盖基准——SPEC §2 原文语义）
- 新档位：75%×128k = **96k tokens 触发**，压掉已用的 20%；emergency 85%（~109k）、hard 95%（~122k）——全部远低于 DSH 自身的 1M@80% 急救，两层代谢不打架
- 备份：`备份/rofm-config-预调窗-20261108-1803.json`（改前已拷）
- 沙箱：目标在工作区外（C 盘 DSH home），首次 edit 被工作区沙箱拒 → 按规矩带理由升级一次；弹窗被错过（老刘不在电脑前）→ 他回来说「再来一遍」，二次通过
- **生效：热加载**——插件 config.json 的 _readme 声明「下一次用户消息/模型步骤前按文件内容自动热加载（坏 JSON 保留上一份）」，无需重启
- **验证判据（行为级，不靠「看着执行了」）**：下一条用户消息后，`memory/sessions/<本会话>/stats.jsonl` 的 recall 行 `windowTokens` 应从 `1000000` 变 `128000`。JSON 语法已 `ConvertFrom-Json` 过
