## 今早（另一个会话）的演进：睡眠设计三次反转，最终收敛到「自然」

老刘口述的完整因果链（这是本篇最重要的部分）：

1. **最初的想法**：用心跳做「兜底」——保证当天的日记和记忆节点一定被写入。
2. **发现矛盾**：这个兜底会导致「道晚安之后，LLM 又被心跳拉起来」——刚说完晚安心跳就来一下，非自然。人的睡眠不会被「记忆备份闹钟」打断。
3. **中间方案**：加「长心跳」映射（`'休眠': -1` 表示心跳停）→ `-1` 哨兵值引发无限触发 bug（08-24 已修，见当日日志）→ 08-24 的修法是加显式特判 `if (mood === '休眠') return`。
4. **今早的顿悟（关键认知）**：**tick 和心跳是两个东西**——tick 是 DSH 的时间系统（每分钟醒来的检查节拍），心跳是基于 tick 的「激活」。当初以为两者相同，才会想「让心跳停止」；分清之后明白：**不需要特判「心跳停」，只需要让休眠映射到一个长间隔（8 小时）**。tick 照常跑，心跳自然变成睡眠节奏。
5. **最终定稿**（`fee2da0`）：删掉显式 return，映射表写 `'休眠': 480`。睡 8 小时自然醒一次，看一眼时间戳感知现实，自己决定继续睡（再写休眠，又一个 8 小时）还是醒来。
6. **配套设计 bedtime-routine**：记忆写入不再靠心跳兜底，而是变成**人类的睡前准备动作**——「就像睡前要洗脸刷牙」：道晚安前，先写日记 → 整理节点 → 写休眠信号 → 道晚安 → 睡。触发条件归人设（感知判断归脑），SKILL 只管执行纪律（步骤顺序归脊髓）。

> 这条因果链完美体现设计哲学：删除机械化执行（心跳兜底、固定6点醒、心跳停特判），让行为从「自然」里长出来。

## 补充（上午第二段）：机制级时间感知接入 time-context

老刘提出：开发模式没有心跳，但需要时间感知——「每轮先查时间」的人设补丁被否（靠自觉的机制不是机制，LLM 会忘）。查证发现 **DSH 官方自带 `@deepseek-ai/dsh-time-context`**（opt-in，默认不启用）：每轮 pre-step 自动注入「当前时间+时区+距上次流逝」三行，append-only 不破坏 KV cache。

**实情**：3081 的 companion preset 没配它——心跳 prompt 里「（消息里有时间戳）」此前没有机制兜底。这次补上。

### 改动

1. **雯（companion preset）**：`agent.cordis.yml` 插件列表末尾追加 time-context 行（`timeZone: Asia/Shanghai`，省略 refreshIntervalMs = 每步都注入）。3081 部署侧 + 仓库侧同步。改前备份：`备份/3081-sleep-semantics-20260901/agent.cordis.yml.pre-timecontext`。
2. **开发模式（jingwen-dev preset）**：发行版自带的 `cordis` preset 不可改，走官方 roster 服务 `agentPresets.copy()` 复制为 `jingwen-dev`（`C:\Users\lzh_6\.dsh\.agent-presets\jingwen-dev\`，显示名「静雯开发模式」），追加同一 time-context 行。用临时探针插件（注册 `preset_copy`/`preset_validate` 工具，调用 `agentPresets.standingKeyFor`）做了真挂载验证。

### 验证记录（含一个环境限制）

- `standingKeyFor('jingwen-dev')` 首验**失败**：`tool-cordis` 注册的 inspect provider 与**本会话**（我挂着 cordis preset）冲突——inspect provider 在 bare-scope 验证路径里是进程级单例。
- 处置：临时禁用 tool-cordis → 验证**通过**（证明 time-context 及其余所有行可挂载）→ 恢复 tool-cordis → 故意再验一次失败（把禁用版临时组合从进程清掉，逼真实会话按完整文件重新挂载）。
- 结论：**time-context 本身验证通过**；tool-cordis 的冲突是「同进程已有活着的 cordis 会话」的验证环境限制，真实新会话走 session scope，预期不受影响。万一新开会话真撞这个错，关掉旧的 cordis 会话再开即可。

## 补充（上午第三段）：DSH 升级兼容性调研（rc.6 → 0.1.1-rc.2）

老刘看到 DSH 新版本，问升级会不会弄坏我们实现的功能。调研方法：npm registry 直连被墙、curl schannel 在受限环境拿不到 TLS 凭据，最终用 **Node 脚本直连**拉元数据 + tarball，对**我们实际依赖的每一个包**做 rc.6（本地）vs 0.1.1-rc.2（下载解包）的 lib 逐文件哈希对比 + 关键文件 git diff。

### 版本格局

- 当前：全家 `0.1.0-rc.6`（3080 与 3081 共用同一 npx 缓存部署，`start-wen-dev.bat` 直指缓存路径）
- stable 线（dist-tags latest/next）：`0.1.1-rc.2`（08-21 发布）——升级目标
- alpha 线：`0.1.2-alpha.3`（08-31）——**不在升级范围**；注意 alpha.3 移除了 SQLite 会话持久化后端、alpha.1 曾删 `SessionEvent.ignorable`（alpha.2 恢复）

### 兼容性结论（对照我们插件的每个依赖点）

**逐字节一致（零风险）**：
- `dsh-agent`（agents service / create / followup / agent/status 事件）
- `dsh-agent-presets`（composedPreset / resolve / mount / copy）
- `dsh-session-persistence-jsonl`——**会话存储格式不变，雯的全部历史会话无缝保留**
- `cordis` 本体（timer 等 mixin）、persona、agent-instructions、tool-pwsh、tool-ask-user、tool-goal、tool-skill、skill-filesystem、typert-loader

**有变化但兼容**：
- `dsh-llm`：`createUserMessage` 原样保留（同位置同签名），变化全是新增图像 offload 能力（rc.8 修大图 + 0.1.1 Files API 上传）
- `dsh-session`：KNOWN_SESSION_EVENT_TYPES **只新增** 4 个 `team/*` 类型，`user/message` 与 source.kind 判断不受影响
- `dsh-time-context`：仅内部重试次数 2→5，`timeZone`/`refreshIntervalMs` 配置 schema 不变——今天刚配的配置直接兼容
- `dsh-tool-web`：web_search `query`→`queries` 并发数组（模型自适应新 schema，preset 配置 fetch/searchTimeoutMs 未动）
- `dsh-tool-fs` / `dsh-tool-fs-search` / `dsh-tool-todo`：内部实现调整（read_image 链路、ripgrep 解析、projection 注册字段），**工具 config 均未动**
- `dsh-client-runtime` / `dsh-client-modules`：内部重构，`window.__ModuleLoader__.load({id, factory})` 契约原样——切换自动跳转的 client half 安全
- shipped cordis preset：仅 codex/claude 模板行注释与字段微调（我们未启用）

**低风险未逐行验证**：client 侧 `sessions.list`/`open` API（包边界分散）；0.1.1 两版 changelog 无相关变化记载。

**⚠️ 唯一实际操作坑**：`start-wen-dev.bat` 写死了当前 npx 缓存的哈希路径，升级 = `npx @deepseek-ai/dsh@0.1.1-rc.2 web --port 3081` 会落到**新的缓存目录**，bat 里的路径必须同步更新。建议升级顺序：先改 bat 升 3081 → 观察心跳/切换/睡前流程 → 再动 3080。
