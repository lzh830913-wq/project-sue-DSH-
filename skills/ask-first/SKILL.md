# 先问后答（ask-first）

> 原始出处：老刘发来的一条提示词——**「回答前先向我提问，一次只问一个问题；根据我的回答继续追问，直到有 95% 的信心完全理解我的真实需求和目标时，再给出最终方案。」**
> 本 SKILL 把它落成可执行纪律，**并补上原提示词缺的那一半：熔断**。2026-09-27 教训——**纯提示词的「追问到 95%」没有上限，会把会话问死**。

## 一、为什么要有它

反例（2026-09-27 收图问题，同一晚三次跑偏）：

| 次数 | 我给的"最终方案" | 实际 |
|---|---|---|
| 1 | 「会话里已有图片，模型选择器锁住了」 | 猜的，未验证 |
| 2 | 「适配器把 `inputModalities` 写死成 text，官方路由永远不支持」 | 半对——只是那一版没实现 |
| 3 | 老刘点破：「3081 能看图，差异在版本」 | **他才是对的** |

三次都在 ~60% 把握上就开工，代价是老刘陪着我在错方向上走了一圈。**信息不足时，提问比动手便宜得多。**

## 二、怎么问（三个硬约束）

1. **一次只问一个问题**——多问会稀释回答质量；要问第二件事，等这一问的回答回来。
2. **必须带候选选项**：用 `ask_user_question` 工具问（例如「A/B/C 你选哪个」），**不要只在正文里写一句话然后停下**。
   > **这是本次会话卡死的直接原因**：原提示词模式下，模型只输出一句追问就结束回合，等待对方的回应——**对话停在半空、看起来像卡死**。带选项的结构化提问才是一个能闭合的回合。
3. **每个问题都要说明「为什么问」**：让回答者知道不问清会付什么代价，回答才有的放矢。

## 三、什么时候必须问（触发条件）

- 目标 / 范围 / 验收标准**有多种合理解释**；
- 要做**设计决策或方向选择**（改架构、换路线、动别人在用的东西）；
- 要**改老刘的配置、实例、或不可逆的东西**；
- 发现自己正基于**未验证的假设**往下推（尤其"我觉得应该是……"）；
- 已经连续两次改动都没解决同一个问题——**停下来问，别加第三次猜测**。

**不用问、直接查、直接干的**：
- 只读查证、定位、比对版本、读日志（**能自己查出来的一律不问**——问之前先穷尽查证，问的是"查不到的东西"）；
- 线上止血 / 服务起不来时的应急恢复（先止血，事后补问）；
- 老刘已经明确指定过的动作。

## 四、熔断（原提示词缺的那一半 · 最重要）

**"问到 95% 再给方案"必须有刹车，否则会把会话问死。**

1. **提问上限：同一个任务最多 3 轮**（每轮一个问题）。第 3 轮的答案到手后，**必须给出方案**，不许继续问。
2. **到上限就给「当前最佳方案 + 显式假设」**：
   - 明确标出哪些前提是假设（例如「假设你要的是 X；若是 Y，则改法是……」）；
   - 说明**怎么验证**（改完看什么现象算对）；
   - 说清**回滚方式**。
3. **一有实质结论就落盘**：每轮问答的定论写进 `进度快照.md` 或 `开发日志/`，**不要只活在上下文里**——万一会话卡死/重启，新会话读文件就能接上，不必重问一遍。
4. **卡住时的自检**：如果发现自己**连续两轮都在问同一件事**，或问题里已经包含答案——**立刻停止提问，转为给出方案**。

> 一句话：**提问是为了拿到方案，不是为了问到完美。3 轮封顶，然后带着假设动手。**

## 五、自检清单（每次动手前过一遍）

- [ ] 我现在的把握有多少？说不清就是不到 95%。
- [ ] 不确定的地方，**能查吗**？能查→去查（先查后说）；查不到→问。
- [ ] 这个问题**值得占用老刘一轮**吗？还是我自己就能定？
- [ ] 这一轮是第几轮？到 3 了没有？
- [ ] 有没有未落盘的结论？（有 → 先写文件）
